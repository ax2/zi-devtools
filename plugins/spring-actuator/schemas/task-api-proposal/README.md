# Background task profile proposal

Proposed alignment: Studio-owned `plugin.task.lifecycle.v1@1.0.0-preview.1`. Studio currently documents this as an unimplemented draft. This proposal does not add that profile to `plugin.json`, grant network access, or claim Studio compatibility.

The task operation ID is `devtools.spring-actuator.run.v1`. A View may submit only `{schemaVersion, idempotencyKey, operationId, input:{origin,endpoints}}`. The trusted Studio gateway injects plugin ID/version, workspace, profile version, runtime/session identity and transport request ID; the Host verifies that identity again for every operation. Host creates an opaque `taskRef`. The View cannot select or submit its own taskRef, identity, path, result reference, permission grant, token, arbitrary endpoint path, or report metadata. Replaying an idempotency key with identical canonical input returns the same task; different input returns `task_idempotency_conflict`.

The Host owns persistence independently of `super_agent_tasks`, enforces owner checks, and records append-only events with increasing sequence numbers. Nonterminal task states are `queued`, `running`, and `awaiting_confirmation`; terminal states are `succeeded`, `partial`, `declined`, `failed`, `cancelled`, `revoked`, and `interrupted`. Each step is one of `actuator.health`, `actuator.info`, or `actuator.metrics`. Before each HTTP side effect, the Host asks for a fresh confirmation bound to the exact task, step, target and grant generation. A decline produces no request. HTTP uses the separate `service.http.get.v1@1.0.0-preview.1` Host capability; it does not expand its permission or safety limits.

The View receives only opaque `taskRef`, bounded state, step IDs, stable error codes and redacted summaries. For a step awaiting confirmation, the Host issues an opaque `confirmationId` bound to that task, step, canonical target, expiry and grant generation; the View may echo that value but cannot mint or alter it. The Host rejects missing, stale, mismatched or replayed IDs before any side effect, and revocation invalidates outstanding IDs. The View never receives a `resultRef`, response bodies, credentials, raw network errors, file paths or resource contents. Results flow through Studio's separately versioned result/resource pipeline. Cancellation returns `requested` while work may still be stopping and `finished` for an already terminal task; terminal `cancelled` is recorded only after the operation stops and no further side effect can occur. Revocation, disable/uninstall, workspace close and shutdown stop the owned task and invalidate grants. Restart recovery resumes only queued work after revalidation; in-progress work becomes `interrupted` unless the Host explicitly implements idempotent recovery with fresh authorization. Pending confirmation requires a new Host-issued confirmation.

The proposed request/response mapping is:

| Provider operation | Studio route | View payload schema |
| --- | --- | --- |
| Submit | `POST /v2/plugin-tasks/submit` | `submit.schema.json` → `submit.response.schema.json` |
| Read current state | `POST /v2/plugin-tasks/snapshot` | `snapshot.request.schema.json` → `snapshot.response.schema.json` |
| Replay ordered events | `POST /v2/plugin-tasks/events` | `events.request.schema.json` → `events.response.schema.json` |
| Confirm one step | `POST /v2/plugin-tasks/confirm` | `confirm.request.schema.json` → `confirm.response.schema.json` |
| Cancel | `POST /v2/plugin-tasks/cancel` | `cancel.request.schema.json` → `cancel.response.schema.json` |

The trusted parent bridge holds the desktop token and injects/verifies plugin, runtime, session, workspace and profile identity; the View never calls these routes or receives the token. The Host sends `confirmationId` to the View only as a challenge bound to a pending step; returning it is not itself permission, and the View cannot construct the confirmation record or grant. Its `idempotencyKey` is a durable task-creation key and is distinct from the bridge's transport `requestId`. Lifecycle only schedules an operation handler registered by Studio and composed from separately declared capabilities. It does not authorize arbitrary plugin background code, process execution, networking, or file writes. The Actuator handler still uses only the separately granted `service.http.get.v1`; saved reports still use the separately published result/resource profile.

Snapshots expose the current state, latest sequence, bounded step states and immutable terminal record. Event replay uses `afterSequence`, bounded `limit`, `nextSequence`, `hasMore`, retained-sequence bounds, `cursorError` and `snapshotRequired`. Duplicate events are ignored by sequence; a gap requires a snapshot; cursor errors return no events. Host also enforces the Studio draft retention defaults: at most 256 events per task, 1 KiB per event payload, 1,000 retained tasks per workspace, and 30 days for terminal records. JSON Schema does not prove ownership, idempotency, ordering, cross-field equality, cancellation finality or side-effect absence; these remain executable Host conformance requirements.

Schemas cover submit, decision, snapshot, replay, cancel, event, terminal, revocation and stable errors. `vectors.json` covers lifecycle and security behavior; `cursor-vectors.json` covers replay relationships; `event-vectors.json` checks schema shape and terminal ordering/binding. The provider verifier is intentionally a finite custom keyword validator, not a full Draft 2020-12 implementation; it runs the documented positive/negative schema vectors plus semantic cursor, event and capture-bound report checks. Studio must run its own standard implementation and runtime conformance before accepting this proposal.

The exact origin policy, DNS pinning/revalidation, address-class denial, OS TLS roots, request/response limits and redaction requirements remain the HTTP Host's responsibility. The profile remains proposal-only and is not declared in manifest 0.1.1.
