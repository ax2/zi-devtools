# 认证增量升级 0.2.0（开发中）

设置→程序更新→便携版升级共用一个准备入口。只在用户主动准备时联网，先验证原有schema1完整发布清单；两件增量元数据都不存在时使用完整EXE。只有一件、签名错误、基线清单格式错误或目标绑定错误时停止，不回退。MSI继续使用完整安装器，不把补丁覆盖到受管理组件内。

## 协议与匹配

增量清单`update-delta.json`及其`update-delta.sig`使用独立消息域`ZiDevTools portable delta v1`末尾NUL加原始JSON字节，Ed25519公钥来自与完整更新相同的内置信任配置，且同次发布两种清单必须由同一公钥签名。原有完整清单schema1和三附件数量保持不变，旧客户端可忽略新资产并继续完整包升级；绝不从服务器读取新的公钥。

清单schema1绑定源/目标SemVer、原始完整清单SHA-256及有序双EXE条目：旧文件名称/大小/摘要、补丁名称/大小/摘要和目标文件名称/大小/摘要。目标与已认证完整发布文件必须完全一致；每件补丁必须小于未压缩目标EXE。清单/签名沿用512KiB/1KiB上限，源/目标/补丁各最大128MiB。严格拒绝未知字段、重复/错序文件、路径或版本混淆。

只有当前编译版本和两个本机程序的大小/摘要均匹配时才下载补丁。未匹配或没有增量时明确显示使用完整包的原因，不把源文件损坏称为可用增量。准备期间源内容改变也拒绝；下载、重建、取消与暂存都在后台。下载进度在认证选定方案后按实际两个补丁或完整EXE大小计，准备结果显示实际程序内容字节、相对未压缩EXE的节省比例，元数据不计入该比例。

每件补丁先核对认证大小/摘要，再有界解压重建，并核对包头源/目标版本、源摘要以及重建EXE与完整发布的目标摘要。包内可能是分块差分，也可能是更小的压缩完整内容；因此“增量准备”表示经过认证的更新内容包方案，不能把压缩完整内容的节省称为源块复用。恢复副本/退出助手和程序目录事务完全复用[便携升级](portable-updates.md)，助手再次认证完整清单与已重建目标。不会执行下载的补丁或从补丁生成脚本。

## 发布工程

Release工作流只在一次性Windows托管CI收集最高的较早正式版双EXE与SHA256SUMS，先检查附件身份/大小再下载并核对完整唯一三项旧摘要。首个正式版没有旧版时只发布完整包；旧版查询或完整性失败时发布失败，不忽略错误。旧版SHA256SUMS可能没有签名，其用途是核对所取基线；真正用于应用的基线摘要由新发布私钥签名绑定，不能声称历史发布已有签名。

`sign_update`可增加`--delta-from BASELINE_DIR SOURCE_VERSION`。生成后逐字节重建自验，只有双包都小于目标EXE才产出两件`.zidelta`和两件独立增量元数据；否则保留完整发布。签名和自验完成才发布所有资产，失败不创建Release。未新增ZIP，不读取或轮换发布私钥，仅复用既有本机专用凭据或Actions环境密钥流程。

## 验证与限制

默认单测覆盖独立消息域/错误信任/目标清单绑定/未知字段、真实块复用双包重建、错误源/补丁篡改/取消，以及认证输出进入生产便携暂存→文件应用→显式恢复并保留用户文件。另有一次性CI读取真实历史发布双EXE、生成当前优化EXE，使用临时测试签名在夹具目录重建/应用/恢复；不运行程序、不安装MSI，临时测试公钥不进入生产信任配置。

首次正式签名Release、真实网络下载到助手重启的增量端到端流程仍需验收，夹具不能替代。只有一组历史基线，未匹配版本使用完整包；没有MSI增量、断点续传、启动健康握手/自动回滚、数据迁移及旧副本清理UI。准备阶段可能同时持有源/补丁/目标多个缓冲区，遵守单文件大小边界但尚无低内存流式重建。
