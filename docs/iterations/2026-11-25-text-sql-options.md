# Text 0.4.2 · SQL 方言与格式

Studio 工具目录中的 SQL 格式化保留 `devtools.text.sql.format`。用户可以省略选项，得到原有的通用方言、四空格和大写关键字输出，或选择 PostgreSQL、MySQL、SQLite、SQL Server、两空格、Tab、小写及保留关键字原样。只有 SQL 能力和它对应的 Pi 工具接受这些选项。插件自带文本 View 仍使用通用默认值。

输入继续最多 8192 UTF-8 字节，序列化请求和结果各最多 48 KiB。格式化复用独立版的纯 Rust 核心，保留 SQL 中的参数和受保护字面量。MySQL 与 SQLite 沿用独立版的通用 tokenizer 和方言保护规则。这里提供文本格式化，没有连接或执行数据库，也没有语义校验。合成 Windows Worker 请求已覆盖四个专用方言、默认字节、布局、标记冲突、非法值和 8192 字节 UTF-8 正例。致密的短语句脚本仍可能耗尽运行预算。

原有 0.4.1 冻结包保留。本文只记录提供方候选和直接 Worker 结果。Studio 安装、工具中心原文件导入及结果下载、升级和 Pi 权限需接收方复验。

## 运行预算定位

- Windows 生产 Worker 的首个选项原型和旧 0.4.1 都拒绝合成的 8192 字节密集通用短语句，返回 `WASI fuel exhausted`。五方言的长 UTF-8 字面量在相同字节上限成功。限额保持 10M fuel、5 秒、64 MiB。
- PG dollar 字面量和 SQLite 方括号密集输入中，旧临时保护算法对全输入与剩余输出反复查找标记。单遍收集原有标记冲突、按索引扫描输出一次后，两种 2 KiB 合成脚本在单独的成本诊断中从超过 100M 降到约 13.76M 与 17.93M。两者依旧超过正式预算，保留真实 Worker 的失败。原有标记宽度、字节与参数保持一致。
- 单独的 `sqlformat 0.5.0` 分段诊断将 8 KiB 密集通用样例定位到 tokenizer，其中每个命中词会对剩余输入做整段大写转换。仅在临时副本消除重复分配后，成本由约 128.08M 降到 30.59M，仍超正式预算。本候选保持上游依赖锁定。后续可继续验证 tokenizer 的等价低成本路径，再评估是否需要单独的 SQL 运行策略。
